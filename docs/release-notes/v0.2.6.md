pictkura 0.2.6 adds one thing to the viewer: taking the picture you are looking at out of it.
Copy it to the clipboard, or save it to a file. Nothing is developed — from a RAW you get the
display JPEG the camera embedded, which is what the viewer was already showing you.

## What's new

**The viewer can hand you the picture it is showing.** Two buttons at the top right — 📋 to
the clipboard, 💾 to a file — and `Ctrl+C` / `Ctrl+S` (`⌘C` / `⌘S` on macOS).

What comes out depends on what the file is:

| File | What you get |
|---|---|
| RAW | The display JPEG the camera embedded, byte for byte |
| HEIC, TIFF | Packed into a JPEG, the same way the viewer does it |
| jpg, png, webp, avif, bmp, gif, svg | **The original file, copied** |

For a photo the app can display directly, nothing is re-encoded — the shooting information
(Exif) and the colour profile (ICC) survive, because the file is simply copied. The saved
file also keeps the original's modification time, so a folder you extract thirty photos into
sorts by when they were taken rather than by when you pressed the button.

A RAW is the interesting case, and the honest answer has two halves. The picture is the one
the camera wrote for its own screen, so it appears immediately and looks exactly like what
you were viewing. It is also **whatever size that camera chose**: current bodies embed
something close to full size — a Canon EOS R6 Mark III `.CR3` gives 4320x2880 — while older
ones store as little as 160x120. With no development, that is the ceiling for that file. For
the same reason a picture taken out of a RAW **may carry no Exif at all**; whether the camera
put any into the picture it embedded is up to the camera.

**Buttons that would not work are not shown.** Some RAW files contain no display picture
anywhere — the Blackmagic CinemaDNG and the two old Panasonic `.RAW` in our sample set are
the ones we have. The viewer shows an empty frame for those, and extraction would fail for
exactly the same reason, so the buttons and the keys are simply absent. SVG can be saved but
not copied: there is no rasteriser in the app to turn it into pixels for a clipboard.

**Saving starts where you saved last time**, and your Pictures folder the first time. It
never writes over the photo it came from: if you point the dialog at the original and agree
to replace it, the save is refused and says so, rather than leaving you with an empty file.

Measured on an Apple Silicon Mac, release build: a `.CR3` whose embedded picture is 4320x2880
goes to the clipboard in **64–74 ms**. A TIFF is the one format the viewer rounds down for
display, and saving does not round it — an 8000x6000 TIFF comes out at full size in 210 ms.
The clipboard does take the rounded picture, because a bitmap that large costs hundreds of
megabytes on the way to the operating system and nobody pastes a picture that size.

**macOS shows its own dialogs in your language.** The app bundle never declared which
languages it supports, so AppKit treated it as English-only: on a Japanese Mac the save
panel came up with a Japanese title and `Save As`, `Where`, `Cancel` underneath it. This
affected the folder picker and the delete confirmation too, not only the new save dialog.
The bundle now declares Japanese and English, and those panels come up in the language you
use. The menu bar across the top is still English — that menu is built by the framework and
is a separate thing to fix.

| You want | File |

| Windows 10/11, the usual case | `pictkura_0.2.6_x64-setup.exe` — no administrator rights |

Neither build is code-signed, so Windows shows SmartScreen and macOS shows Gatekeeper on
first launch. The [README](https://github.com/Harusame64/pictkura#readme) walks through
both, including the extra steps macOS 15 needs.

## Upgrading from 0.2.5

On Windows, run the installer over the top of the old one. On macOS, unzip the new
`pictkura.app` and replace the old one where you keep it — the Gatekeeper steps in the
[README](https://github.com/Harusame64/pictkura#readme) apply again, because the app you
just downloaded is a new file as far as macOS is concerned.

Your library, settings, favourites and picks stay where they are. Nothing is re-read and no
thumbnails are rebuilt: this release changes what the viewer can do with a photo, not how
photos are read in.

## Known gaps

**Copying a HEIC to the clipboard was not measured.** A HEIC has to be unpacked by the
operating system and repacked, which this project has measured at 0.6–1 s elsewhere; the
buttons dim while that runs. The sample library used for these measurements is RAW, so the
number for HEIC is reasoning rather than a measurement, and is written here as such.

**A very large picture costs what it costs.** Saving is deliberately not size-limited, and
the ceiling that exists is the decoder's rather than ours: a 104-megapixel TIFF is refused
outright, so the viewer cannot show it either and the buttons stay hidden. A 169-megapixel
PNG does go to the clipboard, in 1.5 s and about 1.3 GB of memory. No camera made is larger
than 102 megapixels, so this is a scan rather than a photograph, and it is one press you
asked for.

Everything from 0.2.5 still applies. Video thumbnails go only as far as the operating system
can open the container, and the frame taken is always the first one. Linux has no route
wired up for any of this, and there is no Linux build. `.m2ts` and `.avi` appear in the grid
but do not play inside the app. There is still no sort order for search results (newest
capture date first), no UI to rebuild the search index, and imports cannot be cancelled once
started. A RAW that declares nothing anywhere still shows no size. The full list is in the
README.

# 日本語

pictkura 0.2.6 は、ビューアにひとつだけ足しました。**いま見ている絵を、そこから取り出す**
ことです。クリップボードへコピーするか、ファイルに保存します。現像はしません——RAW から
出てくるのは**カメラが埋め込んだ表示用の JPEG** で、ビューアが見せていたのもその絵です。

## 新しくなったところ

**ビューアが、いま出している絵を渡してくれます。** 右上のボタン2つ——📋 でクリップボードへ、
💾 でファイルに——と、`Ctrl+C` / `Ctrl+S`（macOS は `⌘C` / `⌘S`）。

何が出てくるかは、元のファイルによります:

| ファイル | 出てくるもの |
|---|---|
| RAW | カメラが埋め込んだ表示用 JPEG。**そのまま** |
| HEIC・TIFF | JPEG に詰め直したもの（ビューアが出しているのと同じ作り方） |
| jpg・png・webp・avif・bmp・gif・svg | **原本をそのままコピー** |

そのまま表示できる写真は**一度も詰め直しません**——撮影情報（Exif）も色の情報（ICC
プロファイル）も残ります。ファイルをコピーしているだけだからです。保存したファイルは
**元の更新日時も引き継ぎます**。30枚まとめて取り出したフォルダが、押した順ではなく
**撮った順**に並びます。

RAW が面白いところで、正直に言うと答えは二段構えです。出てくるのはカメラが自分の画面用に
書いた絵なので、**すぐ出ますし、見ていたものとまったく同じ**です。同時に、大きさは
**そのカメラが決めたぶん**です: 最近の機種は原寸に近いものを埋めていて——Canon EOS R6
Mark III の `.CR3` なら 4320x2880——古い機種では 160x120 しかないものもあります。
現像しない以上、そこがそのファイルの上限です。同じ理由で、**RAW から出した絵には
撮影情報が入らないことがあります**。カメラが埋め込んだ絵に Exif を付けているかどうかは、
機種によります。

**効かないボタンは出しません。** 表示用の絵をどこにも持たない RAW があります——手元の
見本では Blackmagic の CinemaDNG と、古い Panasonic の `.RAW` 2枚です。ビューアでも枠だけに
なるもので、抽出もまったく同じ理由で失敗するので、**ボタンもキーも出しません**。SVG は
保存だけできます。クリップボードへ載せる画素に起こす道具を積んでいないためです。

**保存は前回保存した場所から始まります**（初めてのときは「ピクチャ」）。**元の写真の上には
決して書きません**: ダイアログで原本を指して「置き換える」と答えても、保存は断られて
そう言います。空のファイルだけが残る、ということにはなりません。

Apple Silicon の Mac・release ビルドで実測: 埋め込みの絵が 4320x2880 の `.CR3` を
クリップボードへ載せるのに **64〜74ms**。TIFF は表示のときだけ縮めている唯一の形式で、
**保存では縮めません**——8000x6000 の TIFF が原寸のまま 210ms で出ます。クリップボードの
ほうは縮めた側を渡します。それだけの大きさのビットマップは OS へ渡る途中で数百MBかかり、
そんな大きさの絵を貼る人はいないからです。

**macOS が、OS 自身のダイアログを日本語で出すようになりました。** アプリのパッケージが
「どの言語に対応しているか」を名乗っていなかったので、AppKit は英語のみのアプリとして
扱っていました。日本語の Mac でも、表題だけ日本語で、その下は `Save As` / `Where` /
`Cancel` という混ざり方をしていたわけです。**これは新しい保存ダイアログだけの話ではなく**、取り込み先を
選ぶダイアログも削除の確認も同じでした。いまは日本語と英語を名乗るので、お使いの言語で
出ます。**画面上部のメニューバーは英語のまま**です——あれは土台のフレームワークが
組んでいるもので、別に直すものです。

## 0.2.5 からの更新

Windows はインストーラをそのまま上書きで実行してください。macOS は ZIP を展開して、
置いてある `pictkura.app` を新しいものに置き換えてください——**Gatekeeper の手順は

ライブラリ・設定・お気に入り・選別の印はそのまま残ります。**読み直しもサムネイルの作り直しも
起きません**——この版が変えたのは「ビューアが写真に対して何をできるか」であって、
写真の読み込み方ではありません。

## まだ出来ないこと

**HEIC のコピーは測っていません。** HEIC は OS に展開させて詰め直す必要があり、その手間は
このプロジェクトの別の場所で 0.6〜1秒と実測しています。走っている間はボタンを伏せます。
今回測ったライブラリは RAW なので、**HEIC についての数字は推測であって実測ではありません**。
そのまま書いておきます。

**とても大きな絵には、それ相応の負荷（時間やメモリ）がかかります。** 保存には意図して
上限を掛けていません。上限があるとすればそれはこちらではなく展開器のもので、**1億画素の
TIFF はそもそも拒否されます**——だからビューアにも出せず、ボタンも伏せたままです。
1億6900万画素の PNG はクリップボードへ通り、**1.5秒・メモリ約1.3GB** かかります。
実在するカメラは最大でも1億200万画素なので、これは写真というよりスキャンで、しかも
ユーザー自身が意図して実行した1回限りの処理です。

0.2.5 までの話はそのまま残っています。動画のサムネイルは OS がコンテナを開ける範囲まで、
取り出すコマは常に先頭です。Linux は経路そのものが無く、配布物も出していません。
`.m2ts` と `.avi` は一覧には出ますが、アプリ内で再生できません。検索結果の並び替え
（撮影日の新しい順で固定）、検索索引の再構築UI、取り込みの中断はありません。どこにも寸法を
申告していない RAW はいまも寸法が空のままです。全部は README にまとめてあります。
